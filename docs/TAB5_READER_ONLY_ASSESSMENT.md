# Tab5 专用阅读器精简评估

评估日期：2026-10-26。基线提交：`7230e8e`。以下保留当时的方案与测量边界。

2026-10-27 已在独立分支 `codex/tab5-reader-only` 实施专用板型、离线阅读 UI 与按需热点传书。
实现、使用和验证边界见 [Tab5 Reader 独立阅读固件](TAB5_READER.md)；下文“本次未裁剪”等描述指评估时的旧固件。

## 结论与产品范围

可行，建议基于当前 ESP-IDF 6.0.2 工程制作独立的 `m5stack-tab5-reader` 构建变体，开机进入书架，仅保留本地阅读、字体、阅读进度、屏幕/电源设置、文件传输和升级。默认离线阅读，进入传书页面时才开启网络服务。

Tab5 原装屏幕是 5 英寸 1280×720 IPS 触摸液晶屏；“墨水屏版本”可实现为黑白/纸色、低干扰的阅读器风格，但软件不能把液晶改成电子纸，也不能获得电子纸断电保留画面的特性。若目标是真正外接/更换电子纸面板，需要先确定面板、控制器、接口和供电，再增加独立板型及显示驱动，不能修改现有 Tab5 引脚定义冒充兼容。

依据：[M5Stack Tab5 官方规格](https://docs.m5stack.com/en/core/Tab5)。

## 精简边界

| 部分 | 处理 | 工程依据与目的 |
|---|---|---|
| LCD、触控、RTC、电池/背光、TF 卡 | 保留 | 已在 `main/boards/m5stack/tab5/` 跑通；沿用原引脚与面板识别 |
| LVGL、FreeType、EPUB、封面与进度 | 保留并拆成阅读模块 | 现有 `han_display.cc` 同时承担大量学习功能，需提取阅读 UI 与服务 |
| ESP32-C6、ESP-Hosted、Wi-Fi 配网 | 保留，按需启动 | P4 通过 C6 提供无线能力；后续传书需要，不应随语音模块一起删除 |
| USB MSC 与本地手动 OTA | 保留 | 便于离线传书、维护及故障恢复；传书/读卡器模式需统一存储互斥 |
| 语音、唤醒/VAD、编解码、云端对话协议、激活 | 从专用变体的初始化及构建中移除 | `Application::Initialize()` 当前无条件启动音频，联网后进入激活流程；仅隐藏按钮仍会运行后台任务 |
| 摄像头、视频及图像识别依赖 | 不初始化、不链接到专用变体 | Tab5 构造函数当前调用 `InitializeCamera()`；分离板级可选能力与阅读需求 |
| 字典、音标、课表、学习计时、天气、留言、翻页时钟、旧闹钟 | 不进入专用 UI；进一步移出构建 | 页面代码、工作队列、定时器与素材需一起裁剪，不能只改主页 |
| NVS 与 TF 目录 | 保持兼容 | 保留 `han_reader`、`display` 键，以及 `handict/books`、`handict/fonts` 与现有封面缓存 |

运行资源收益可预期，但本次没有构建精简固件，不能给出已节省多少 MB 或续航提升倍数。现有固件仍约 5.63 MB；当前分区是双 6 MiB OTA 槽及约 3.88 MiB 资源区。第一阶段沿用分区，避免让普通应用更新变成整机分区迁移；后续按实际 map 与容量报告决定是否调整。

## 推荐实施顺序

1. 新增唯一的阅读器变体与 OTA 身份，补齐 `config.json → build.py → Kconfig → CMake → 板级配置` 链路，保证恰好一个板工厂。保留原学习固件变体，便于对照回归。
2. 从 `HanDisplay` 提取书架、阅读页、字体缓存、进度和屏幕设置；使用小型应用事件循环管理阅读、存储、网络和电源。通过 Board 接口访问硬件，避免把具体 Tab5 类带进阅读核心。
3. 专用启动路径不创建音频任务、不启动摄像头、不进行小智激活/云连接；删除这些功能的编译源、依赖、模型与素材。确认固件大小、启动耗时、PSRAM、CPU 空闲及电池放电数据。
4. 开机进入书架，保留最近阅读、进度条、横竖屏、沉浸式菜单与 LXGW；系统设置只留下屏幕、电源、存储、网络与升级。
5. 加入按需 Wi-Fi 传书，再继续目录、书签和精确字形分页。当前分页仍是字符数估算，精简功能本身不会自动解决复杂 EPUB 排版。

## Wi-Fi 传书的接入设计

首版采用浏览器上传：设备连接现有 Wi-Fi，或开启临时热点；屏幕显示地址/二维码，手机或电脑打开网页上传 EPUB 和 TTF。优先实现局域网浏览器传书，不把 Calibre、OPDS、WebDAV、微信读书全部纳入首版。

可复用工程已有的 `esp_http_server` 和 `HanOtaServer` 接收/分块写入经验，但应由统一 HTTP 服务管理路由，避免两个服务争抢端口。OTA 镜像接口与图书/字体上传接口必须分开。

上传使用固定大小缓冲，不把整本书或整个字体放进 RAM。限制扩展名、文件名和大小，拒绝路径穿越；先写同目录临时文件，校验后重命名，再由工作队列刷新书架。默认避免同名覆盖。会话只在设备进入传书模式后启用，使用屏幕显示的临时会话码；退出即关闭上传服务。

USB MSC 活跃时禁止设备端读写 TF 卡。传书期间暂停可能冲突的扫描/封面缓存和阅读打开操作，避免一边读取字体或 EPUB、一边改写同一文件。特别不能覆盖正在使用的字体。退出传书后恢复原阅读位置。

验收包括大书上传、断线/取消后的临时文件处理、剩余空间不足、中文文件名、同名文件、字体上传、USB 互斥、退出后网络状态，以及 OTA 服务共存。

## CrossMux 与 WhiteOS 的参考价值

[CrossMux 官方 README](https://github.com/0x1abin/crossmux)提供阅读/书库和浏览器传书等无线工作流参考，但当前公开目标列表没有 Tab5，构建使用 PlatformIO/pioarduino。完整固件不能当作 Tab5 的现成镜像；移植需要重新处理 P4、MIPI 显示与触控。更适合借鉴阅读交互及按需网络服务的分层。

[WhiteOS 官方仓库](https://github.com/446599/whiteos)定位为小纸 Pico 的介绍站、网页烧录与固件发布内容，公开目录不能证明完整设备固件源码可复用。其书架、实时字体与阅读设置可作产品参考；不能把网页动画当作刷新速度或光学效果的实机证据。完整复刻其 EPUB/PDF、微信读书及学习功能，也不符合本次“仅保留电子书”的精简目标。

推荐沿用已经实机验证的 Tab5 BSP 和当前阅读能力，打造专用阅读器，而不是先移植另一整套系统。实际电子纸硬件适配作为独立项目范围评估。
